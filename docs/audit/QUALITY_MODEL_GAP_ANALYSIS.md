# Quality model gap analysis

This document compares the current Sindopoly repository against `docs/engineering/SOFTWARE_ENGINEERING_QUALITY_MODEL.md`.

Priority scale:

- `P0`: prevents reliable build, execution, or testing.
- `P1`: security, corruption, concurrency, or core game-flow risk.
- `P2`: broken or incomplete functionality.
- `P3`: architecture, maintainability, testability, or performance issue.
- `P4`: consistency or documentation improvement.

## Current strengths

- Dice randomness already uses an injectable `RandomIntGenerator`, which is a good fit for deterministic tests.
- `MovementService#move` is small and deterministic.
- Backend has begun separating core services (`DiceService`, `MovementService`, `SquareActionService`, `CardService`) from controllers.
- `GlobalExceptionHandler` avoids leaking stack traces for generic internal errors.
- Frontend calls the server to roll dice instead of generating authoritative dice locally.
- Docker Compose defines explicit Redis/MariaDB/backend/frontend services and health dependencies.

## Acceptable current designs that should not be over-engineered

- Keep `MovementService` simple; do not introduce a complex board abstraction unless rules require it.
- Do not add Redis Pub/Sub solely because Redis exists; current direct WebSocket broadcasting is enough until multi-instance requirements are explicit.
- Do not create interfaces for every Spring service. Use interfaces for nondeterminism, external integrations, alternate implementations, or test seams.
- Keep DTOs simple at boundaries, but make internal turn/game phases explicit when modifying game flow.
- Do not optimize N+1-style player detail reads before correctness/security and tests unless measurements show real pain.

## Recommended future application order

1. Add characterization tests around current create/join/start/roll/action/end behavior.
2. Establish server-side identity and authorization for commands.
3. Quarantine direct player-state mutation and money-grant paths.
4. Make turn commands idempotent and per-game atomic.
5. Define explicit game/turn state machine phases.
6. Standardize WebSocket event envelope and subscription authorization.
7. Consolidate Redis schema ownership and remove unsafe `KEYS` paths incrementally.
8. Align frontend API configuration and realtime strategy.
9. Harden MariaDB schema/migration ownership.
10. Clean dead/commented code after tests protect behavior.
