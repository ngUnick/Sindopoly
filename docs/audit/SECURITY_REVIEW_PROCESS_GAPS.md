# Security review process gaps

This document compares the current Sindopoly repository and development process against the reusable security review process in `docs/security/FEATURE_SECURITY_REVIEW_STANDARD.md` and `docs/security/SECURITY_REVIEW_CHECKLIST.md`.

It does not fix the gaps. It records where future implementation work should apply the new process.

Priority scale:

- `P0`: prevents safe build, execution, or verification.
- `P1`: confirmed or likely critical security or integrity risk.
- `P2`: important missing control or broken behavior.
- `P3`: process, testability, maintainability, or defense-in-depth gap.
- `P4`: documentation or consistency improvement.

## Current process strengths

- The repository now has architecture, API, Redis, WebSocket, risk, quality-model, and commenting-standard documentation under `docs/`.
- Backend dice and movement are server-side in `DiceService` and `MovementService`, which supports the backend-authoritative principle for those specific calculations.
- `GlobalExceptionHandler#handleServerError` returns a generic 500 body instead of client-visible stack traces.
- Docker Compose clearly identifies local MariaDB and Redis services, which gives deployment hardening a concrete starting point.

## Highest-priority future work

1. Add characterization/security tests around current game commands before risky refactors.
2. Establish trusted authentication and server-side player identity.
3. Add game membership, host, active-player, and phase authorization.
4. Quarantine or secure direct state mutation endpoints.
5. Add idempotency and per-game concurrency controls to dice/action/timer flows.
6. Design WebSocket subscription authorization and reconnect recovery before enabling realtime commands.
